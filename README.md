# rl-crypto

![CI](https://github.com/Cairnstew/rl-crypto/actions/workflows/ci.yml/badge.svg)
![production](https://github.com/Cairnstew/rl-crypto/actions/workflows/production.yml/badge.svg)
![watchdog](https://github.com/Cairnstew/rl-crypto/actions/workflows/watchdog.yml/badge.svg)

**One CLI and one dataset over two crypto pipelines.** `rl-crypto` fuses the
market side of **tickerkit** with the news-sentiment side of
**ticker-news-signals** into per-(ticker, UTC interval) records — the raw
material for a crypto RL/backtest pipeline.

```console
$ rl-crypto unified ETH/USD                 # fused market + news, one record
$ rl-crypto dataset ETH/USD --from 2026-01-01 --to 2026-01-07 --timeframe 1h
```

```python
from rl_crypto import build_unified, build_dataset

record = build_unified("ETH/USD", lookback_hours=3)
print(record.price, record.latest_sentiment, record.notes)

dataset = build_dataset("ETH/USD", start="2026-01-01", end="2026-01-07", timeframe="1h")
for row in dataset.rows:
    print(row.timestamp, row.close, row.sentiment_score)
```

The two upstreams answer different questions about the same asset; this project
*joins their answers*:

| Side | Upstream | Answers |
| ---- | -------- | ------- |
| Market | [`Cairnstew/tickerkit`](https://github.com/Cairnstew/tickerkit) | Consensus price across venues, 24h change/volume/cap, OHLCV history (provenance-tracked) |
| News | [`Cairnstew/ticker-news-signals`](https://github.com/Cairnstew/ticker-news-signals) | Per-hour VADER sentiment vectors from many keyless feeds, live and reconstructed via Wayback |

- **Free tiers only.** The core path of both upstreams is keyless; nothing here
  adds a credential.
- **Partial-failure tolerant.** If one upstream raises, the other side's data is
  still returned and the failure lands in `notes` (or a `<side>: …` note on the
  dataset). A half-answer is an answer, not a crash.
- **Nothing is fabricated.** An unavailable measurement is `None` plus a flag
  (`market_ok` / `news_ok`, or `has_price` / `has_news` per dataset row) with an
  explanation — never a manufactured `0`.
- **Transparent joins.** The dataset is the **union** of price and news buckets,
  floored onto the same UTC interval. An hour known to only one side is kept and
  flagged, so sparse news history shows up as `has_news: false` rows instead of
  silently shrinking the dataset.

## Layout

This repository is itself a flake + uv project, modeled on the two upstreams:

```
src/rl_crypto/        the unified package (models, unify, dataset, render, export, cli)
src/rl_crypto/features.py   Tier-0 causal features
src/rl_crypto/targets.py    forward-shifted Tier-1 labels
src/rl_crypto/samples.py    features+targets aligned for training
src/rl_crypto/ml/      Tier-1/2: estimators, trainer, outlook, bundle store, serve
src/rl_crypto/pipeline/  production runners behind the `rl-pipeline` command
tests/                offline, mocked suite (CI never touches the network)
tools/                record_live.sh / render_dashboard / install_kernel / build_notebook / validate_notebook / audit / probe
examples/quickstart.py
notebooks/unified.ipynb   generated by tools/build_notebook.py
models/               trained Tier-1 bundles (JSON, committed)
data/                 committed pipeline cache (candle archive + live records + summary)
.zed/settings.json    pins the notebook kernel for the Zed editor
flake.nix             hermetic uv2nix build + dev shell
.github/workflows/    ci.yml (offline) + notebook.yml (live) + production.yml (scheduler) + watchdog.yml
```

## Development environment (Nix)

Python 3.12, uv, ruff, basedpyright, and the notebook kernel all come from the
flake. `uv sync` inside the shell builds the venv from `uv.lock` (path sources
point at the sibling checkouts, so local edits to either upstream are live).

```bash
nix develop                        # enter the shell (first run creates .venv)
uv run rl-crypto unified ETH/USD   # or the wrapper commands below
uv run pytest -m "not live"        # offline test suite
uv run ruff check src/ tests/ examples/ tools/
```

The dev shell sets `LD_LIBRARY_PATH` (zlib + libstdc++), which is what makes the
PyPI wheels for numpy/pandas importable on NixOS — the reason these repos use
uv+uv2nix in the first place.

### Or plain pip/uv (non-Nix)

```bash
uv sync --group dev        # creates .venv from uv.lock
uv run rl-crypto --help
```

**On NixOS, outside `nix develop`, set `LD_LIBRARY_PATH`.** The PyPI wheels for
numpy/pandas link `libz.so.1` and `libstdc++.so.6` by soname, and NixOS has no
`/lib`, so importing numpy fails with `libz.so.1: cannot open shared object
file`. Point it at both libraries from the store:

```bash
export LD_LIBRARY_PATH="$(dirname $(ls -d /nix/store/*zlib*/lib/libz.so.1 | head -1)):\
$(dirname $(ls -d /nix/store/*gcc*-lib/lib/libstdc++.so.6 | head -1))"
```

Check the ELF class before picking one — the store holds both 32- and 64-bit
builds, and a mismatched one fails with `libz.so.1: wrong ELF class: ELFCLASS32`
rather than anything obviously related.

## The unified CLI

```
rl-crypto market  TICKER [tickerkit args…]      # delegate: market snapshot
rl-crypto news    TICKER [tns pull args…]       # delegate: live news pull
rl-crypto news-history TICKER --from … --to …   # delegate: archived news
rl-crypto unified TICKER                        # fused market + news record
rl-crypto dataset TICKER --from … --to …        # joined hourly dataset
rl-crypto sources                               # every upstream source
rl-crypto version
```

`market` / `news` / `news-history` **delegate** to the upstream CLIs, so every
flag they document keeps working (`--report`, `--frames ohlcv`, `--append`,
`--sources`, …). `unified` and `dataset` are rl-crypto's own fused output.

The **production runners** are a second entry point, kept out of the analysis
surface:

```
rl-pipeline run        # grow each ticker's archive, retrain, append a live record
rl-pipeline live       # append one live record per ticker (no training)
rl-pipeline conflicts  # resolve data/ rebase conflicts by merging both sides
rl-pipeline sync       # fast-forward the checkout to the tracking remote
rl-pipeline version
```

Both share one library and one exit-code convention (`0` ok, `1` partial or
failed, `2` usage). Every runner takes `--root` (default: the current working
directory, overridable with `RL_CRYPTO_ROOT`) and `run`/`live` keep the hard
exit that stops abandoned fetch workers from holding the process alive.

```bash
# fused point-in-time record
rl-crypto unified BTC/USD --json
rl-crypto unified ETH/USD --metrics              # one flat row, pipeline-shaped

# joined dataset: JSONL to stdout, file via --output, CSV via --format csv
rl-crypto dataset SOL/USD --from 2026-01-01 --to 2026-01-07 --timeframe 1h
rl-crypto dataset ETH/USD --from 2026-01-01 --to 2026-01-14 --output eth.csv --format csv
```

## Dataset schema

One JSON object per line per UTC interval (JSONL), or one CSV row:

```json
{
  "ticker": "ETH_USD",
  "timestamp": "2026-01-01T00:00:00Z",
  "close": 2500.0, "open": 2499.0, "high": 2505.0, "low": 2490.0, "volume": 12345.0,
  "sentiment_score": 0.42, "article_count": 7, "novelty_flag": true,
  "has_price": true, "has_news": true
}
```

| Field | Source | Meaning |
| ----- | ------ | ------- |
| `close/open/high/low/volume` | tickerkit consensus | Cross-referenced OHLCV bar for the interval (all `None` when no price data) |
| `sentiment_score` | ticker-news-signals | Mean VADER compound across the interval's headlines |
| `article_count` / `novelty_flag` | ticker-news-signals | Headlines in the bucket / any newer than the novelty window |
| `has_price` / `has_news` | rl-crypto | Which side actually answered this interval (union join) |

Both time models are UTC, so an interval aligns with OHLCV bar-open time without
timezone shifting — the same contract as
[`ticker-news-signals/INTEGRATION.md`](https://github.com/Cairnstew/ticker-news-signals/blob/main/INTEGRATION.md).

## ML pipeline (tiered)

On top of the fused `dataset` sits a tiered, structured-ML pipeline. Tiers are
replacement units: each has one job and a stable JSON contract, so a tier can be
swapped (say, Tier 1 gains a scikit-learn backend) without touching the others.
Tier 3 (RL) is deliberately out of scope today; the seam for it is
`Outlook.as_features()`.

| Tier | Module | Job |
| ---- | ------ | --- |
| **T0** | `rl_crypto.features` | Deterministic, **causal** features (lags, rolling vol/gaps, volume z, sentiment level/Δ/EWMA, novelty, calendar). Identical for train and serve — no skew by construction. Windows are measured in *time*, so a data gap withholds a feature rather than silently re-timing it. |
| **T1** | `rl_crypto.ml.tier1` | One structured model per target metric, fit on historical samples. Reference estimators are pure numpy (`ridge`, `logistic`, plus `mean`/`base_rate` baselines). Every model is scored **out of sample** against a constant baseline. |
| **T2** | `rl_crypto.ml.tier2` | Fuse the Tier-1 outputs into one `Outlook` (predictions, probabilities) and publish a composite `signal`/`confidence` **only** for models that earned it. |
| **T3** *(future)* | — | RL consumes T0 features ⊕ T2 outlook as its observation vector. |

Targets (each gets its own model): **`fwd_return`** (regression), **`fwd_direction`**
(classification), **`fwd_volatility`**, **`fwd_volume_ratio`**. All are built by
looking **forward** from a row, while features only look back, so training
labels can never leak into inputs. A horizon label is only defined when its
future sits *exactly* that many intervals away — across a data gap there is no
label, rather than a longer-horizon one wearing the wrong name. `None`
propagates through the whole stack — a missing measurement yields a missing
feature/prediction, never a fabricated `0` (the sole exception is the documented
`has_news`/`sentiment` encoding).

### Every model must beat a constant, out of sample

A fit scored on its own training rows measures memorised noise. Tier 1 therefore
reserves the newest ~20% of rows as a chronological holdout, **ships the weights
fitted on the training split only** (so the published score describes exactly the
artifact in `models/`), and compares each target against a constant predictor on
that reserved tail. The comparison needs a **1% relative** margin: on ~300 rows a
0.1% log-loss difference is noise.

Tier 2 then withholds `signal`/`confidence` for any target that did not clear
that bar, with a note saying why. Point predictions are still emitted — they are
inputs for a future RL observation vector, not claims about the market.

What that verdict currently says across all 15 tracked tickers:

| target | beats baseline | verdict |
| ------ | -------------- | ------- |
| `fwd_return` | 0/15 | **no directional skill** — worse than a constant everywhere |
| `fwd_direction` | 0/15 | **no directional skill** — at or below always-up |
| `fwd_volatility` | 9/15 | modest but real |
| `fwd_volume_ratio` | 15/15 | solidly real |

So the pipeline currently publishes **no directional signal**, which is the
honest reading of hourly price-only data. The volume-activity target is the one
with real out-of-sample skill. Details in [`models/README.md`](models/README.md).

**News is live-only for now.** The production runner is deliberately
market-history-only, so every news feature is constant in training. A constant
column teaches a model nothing and would arrive out-of-distribution at serve
time (the live path *does* have news), so the trainer drops such features
entirely and lists them under `dropped_features`. They light up on their own once
news history is ingested. The production runner is market-history-only today
(it has no news-history switch yet); once the archive carries news, retrain with
`rl-pipeline run --retrain-only`.

```bash
# 1) materialise features + targets for a window (no learning)
rl-crypto features ETH/USD --from 2026-01-01 --to 2026-07-01 --timeframe 1h

# 2) fit Tier-1 models, write a JSON bundle under models/
rl-crypto train ETH/USD --from 2026-01-01 --to 2026-07-01 --timeframe 1h

# 3) live: fused record + recent window -> predictions attached as features
rl-crypto predict ETH/USD --json
```

Python: `train_tier1(build_dataset_samples(dataset, horizon=1), horizon=1)`,
`save_bundle(..., "models/eth-usd.json")`, then
`outlook = outlook_for_dataset(live_dataset, load_bundle("models/eth-usd.json"))`
and `record.predictions = outlook.to_dict()` — the feature addition.

Bundles are committed, diffable JSON; see [`models/README.md`](models/README.md).

## Scheduled production run

One scheduled workflow, [**production.yml**](.github/workflows/production.yml),
owns every cache write. It records **every tracked ticker on every run** —
nothing is staggered or rotated — and picks its mode from the clock:

| cadence | mode | what happens |
| ------- | ---- | ------------ |
| every **30 min** | `live` | append one live record per ticker (market + live news + outlook); no training, no history fetch |
| every **2 h** (even UTC hours) | `train` | grow each ticker's raw-candle archive, rebuild features/labels, retrain its Tier-1 bundle over the whole archive, append the live record |

Both modes fan out as a matrix (`max-parallel: 4`) and stage each ticker's cache
as an artifact; a single `merge` job is the only writer and makes **one commit
per run**. Tickers never race to push `data/`.

Because GitHub's scheduled events are best-effort (delayed under load, and
occasionally dropped), [**watchdog.yml**](.github/workflows/watchdog.yml) runs
hourly, checks the newest commit touching `data/`, and dispatches a `live` run
when the cache is older than `RL_CRYPTO_MAX_AGE_MINUTES` (default 75). That is
what replaces the old local systemd timer — collection is now fully remote.

Forked? See [Forking this repo](#forking-this-repo) below.

The watchlist is defined once, in
[`src/rl_crypto/tickers.py`](src/rl_crypto/tickers.py) — add or retire a ticker
there and every runner follows:

```bash
uv run rl-pipeline run --history-days 60   # whole watchlist: archive + train
uv run rl-pipeline run --retrain-only      # models only, from the committed archive
uv run rl-pipeline live                    # whole watchlist: frequent live points
uv run rl-pipeline live --tickers BTC/USD  # just one, for a spot check
```

`--retrain-only` rebuilds every bundle from the archive already on disk, spending
no upstream quota and appending no live records — the right move after a
feature-contract change, when the bars have not moved but the models are stale.

What the cache holds per ticker (all under the repo; see
[`data/README.md`](data/README.md)), e.g. for `ETH/USD`:

| artifact | contents | growth |
| -------- | -------- | ------ |
| `models/eth-usd.json` | fresh Tier-1 bundle | overwritten per pipeline run |
| `data/eth-usd/candles.jsonl` | **raw market archive**, one OHLCV bar per interval | **only grows** (upsert by timestamp) |
| `data/eth-usd/live.jsonl` | live unified record (market **and** live news) + outlook | appended, capped (default 1000) |
| `data/eth-usd/summary.json` | archive span, **out-of-sample** model quality, outlook, notes | overwritten per pipeline run |

The workflow reuses the sibling-checkout + `uv sync` layout of `ci.yml`, and
the merge job holds the `rl-crypto-cache` concurrency group so two write-backs
can never race. Every write-back re-triggers CI — cached state always lands
green.

**Seed locally first.** Run the pipeline on your machine once before (or while)
relying on the crons — local runs reuse the sibling projects' on-disk caches,
so a big first archive backfill completes here and the scheduled runners only
refresh it afterwards:

```bash
uv run rl-pipeline run --history-days 60 --fetch-timeout 600
```

The first run of a new ticker is the slow one (it backfills that ticker's
archive); later runs only refresh it. A ticker that has never been trained has
no bundle, so dispatch a `train` run for it before the 30-minute `live` cadence
can record it.

## Forking this repo

The repo is designed to be forked per watchlist — including a **one-ticker
fork**, which is the cheapest way to run the whole loop remotely:

1. Fork, then **enable Actions** in the fork (GitHub disables workflows on forks
   until you do). Scheduled runs only fire on the default branch.
2. Set the repository variable **`RL_CRYPTO_TICKERS`** (Settings → Secrets and
   variables → Actions → Variables), e.g. `BTC/USD`. The scheduled runner reads
   it instead of the full list in `src/rl_crypto/tickers.py`; `workflow_dispatch`
   can still override it per run.
3. Optionally set **`RL_CRYPTO_MAX_AGE_MINUTES`** to tune the watchdog, and edit
   the cron in `production.yml` if 30 minutes is more resolution than you need.
4. Trigger a first **train** run (`Actions → production → Run workflow`,
   mode `train`). After that the schedule maintains it.

What it costs: on a **public** fork, standard GitHub-hosted runners are free, so
the default 30-minute cadence costs nothing but wall clock. On a **private**
fork the 2,000 free minutes/month do not cover it — one ticker still means ~3
runner-minutes per run (live + merge), ~4,300 minutes/month at 30-minute ticks.
There, switch the cron to hourly (`0 * * * *`, ~2,100) or every two hours
(~1,100), or use a self-hosted runner.

The upstreams (`Cairnstew/tickerkit`, `Cairnstew/ticker-news-signals`) are read
as public sibling checkouts, so a fork needs no secrets. Only your own fork's
`data/` and `models/` diverge, which is the point: an independent archive, model
set and cadence per fork.

## Notebooks

Notebooks are **generated**, so edit the cells in `tools/build_notebook.py`
rather than the `.ipynb` — the same tooling both upstreams use:

```bash
uv run python tools/build_notebook.py            # regenerate notebooks/unified.ipynb
uv run python tools/install_kernel.py            # re-pin after recreating .venv
uv run python tools/validate_notebook.py         # execute end-to-end (offline: reads data/)
```

`unified.ipynb` syncs the checkout with the tracking remote before reading
(fetch plus a `--ff-only` pull via `rl_crypto.cache.sync_cache`), so it always
sees the latest committed cache; offline — or with local changes in the way —
the pull refuses, the reason is printed, and the notebook still runs on the
files on disk. It reads the candle archive, the live-record stream, and the run
summary under `data/<slug>/`, plus the trained bundle under `models/`.

### Opening it in Zed

Zed discovers notebook kernels through `jupyter kernelspec list`, so a
notebook with no registered kernel just reports "no kernel".
`tools/install_kernel.py` writes an `rl-crypto` kernelspec whose `argv` names
the project interpreter **by absolute path** (`.venv/bin/python`, or the
`nix develop` python). The venv's own `python3` spec is not enough: its `argv`
is a bare `python`, resolved through `PATH`, so which interpreter actually runs
depends on how the editor was launched — and a cell can end up importing a
different `rl-crypto`, or none, than the one you are testing.

The dev shell installs the kernelspec once on first entry; re-run it after any
recreation of the virtualenv, directly or via the flake:

```bash
uv run python tools/install_kernel.py            # from a venv or `nix develop`
nix run .#kernel                                 # same thing, via the flake
```

[`.zed/settings.json`](.zed/settings.json) then pins Python cells to that
kernel via `jupyter.kernel_selections`. `nix run .#notebook` (or
`tools/validate_notebook.py`) executes the notebook under that same kernel, so
what Zed runs is exactly what CI tested.
